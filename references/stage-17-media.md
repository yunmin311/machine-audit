# Stage 17 · 媒体 / 相册治理

## 目的
照片/视频资产的完整性与可检索性。原则：**不推翻用户已有的编修体系**（Lightroom/Capture One/剪映 都是专业 DAM），技能只补"完整性、检索、备份达标"三层。

## 检查项
1. **归档结构识别**：相机原片目录的现有组织方式（按机身/日期/项目），**沿用而非纠正**；识别编修软件与其 catalog 位置。
2. **3-2-1-1-0 达标**：3 副本/2 介质/1 异地/1 离线/0 错误。核心原片仅单盘 = P0（不可再生数据）。评估外置冷备/云端的缺位项。
3. **catalog 备份代数**：编修软件的 catalog/数据库备份代数与时间跨度（如 LR catalog backups）——建议保留最近 3 代，超期清单。
4. **重复副本**：原片在"工作目录/同步目录/导入目录"的多份并存检测（同尺寸+抽样哈希）——典型：手机导入副本、云盘镜像与正本三份。
5. **完整性**：hash 清单存在性（每场景目录一份 manifest 的模式）；无清单时建议 ExifTool 生成（给出命令样例：`exiftool -checksum -r -o manifest .` 类，按实际工具写法）；抽查读回验证。
6. **检索层建议**：现势是"只能翻文件夹"时，建议自托管检索（指向现有目录、不改结构的方案优先——按当前社区共识检索并**带来源与日期**，如 PhotoPrism 类指现有树 / Immich 类手机备份 / PhotoStructure 类去重，选型随版本演进）。
7. **视频资产**：游戏录像/剪辑工程的缓存黑洞（剪辑软件媒体缓存常 50-200GB）与成品目录分离。

## 判定
- 不可再生原片单副本 = P0；catalog 无备份 = P1；检索缺失 = P2；重复三份 = P2（清理需先核一致性）。

## 坑
- 云相册"同步"语义≠备份；哈希大文件前先确认非云占位（conventions）。
- 手机照片与相机原片是**两条流水线**，别合并目录——分别评估。
