# execution-safety · 预览与回退机制设计（v0.7 提案）

> **背景**（用户需求，2026-10-25）：① 执行前能看到"改完之后大概的样子"——最好在虚拟机或某种形式里预览，并让报告指明重要文件都在哪些地方；② 出了问题能回退。
> **结论先行**：整机级"虚拟机预览"在本机不可行（家庭版无 Hyper-V/Sandbox；整机克隆 100GB+ 且慢），而文件操作的预览与回退有更工程化的标准做法——**两段式执行 + 同盘隔离区 + manifest 快照**。虚拟机预览保留为高阶可选。

---

## 1. 预览机制：三层设计

### L1 清单预览（规程/表格形态，尚无统一执行器脚本）
可删除清单 / R 系列表格——精确到路径、体量、理由。这是所有预览的地基。

### L2 树状前后 diff 预览（新增，纯计算、零风险）
对每个待执行批次，从计划确定性生成两个"树"：
- `tree-before.md`：受影响目录的前置树（相对路径 + 体量 + 关键文件标记）
- `tree-after.md`：模拟执行后的树——被删项标注 `[已删除]`，移动项标注 `[已移动 → 隔离区/<路径>]`，保留项原样
用户读 `tree-after.md` 就是"改完之后大概的样子"——不需要虚拟机，因为文件操作的"未来状态"可以确定性推演。**虚拟机才能预览的是系统级变更**（服务/注册表/引导），那些走 §3 的备份材料 + 文本 diff 预览。

> **该预览生成器尚未实现：以下为设计中的调用约定；当前需按本节规程手工生成。**

### L3 隔离区试运行（新增，真实预览的落地形式）
**删除不直接删除，先搬家。** 同盘移动（rename）瞬间完成、零成本：
```
执行批次 N → 所有"删除"对象移动到 <同盘>\_quarantine\<runid>\<原相对路径>
            → 机器继续正常使用 = 你看到的系统状态就是"删除后"的真实样子
宽限期（默认 14 天，overlay 可调）内随时可回退
宽限期满 + 用户再次确认 → 清空隔离区（此时才真正删除）
```
> **该宽限期与执行器尚未脚本化：以上为设计中的调用约定；当前需按本节规程手工执行。**

这就是云盘回收站的机制：**"预览"的终极形式是可逆试运行**——不是看模拟图，而是真的进入删除后的状态但保留后悔药。

### 虚拟机的定位（如实）
- 家庭版无 Hyper-V/Windows Sandbox → 整机 VM 预览在本机需先升级系统或修复 VirtualBox。
- 适用场景：**系统级变更**（服务禁用、驱动卸载、引导相关）在 VM 里先试。设计上把这类动作与文件动作分开，VM 预览只对这类动作强制建议。
- 文件删除/移动类：VM 预览性价比极低（整机克隆 vs 同盘 rename），不采用。

## 2. 回退机制：分层回滚材料 + 操作日志

### 2.1 按动作类型的回滚材料
| 动作 | 回滚材料 | 回滚方式 | 可靠性 |
|---|---|---|---|
| 删除 | manifest（原相对路径+体量+哈希）+ 隔离区副本 | 隔离区移回原位 | 高（同盘 rename） |
| 移动/改名 | (from, to) 对 | 反向移动 | 高 |
| 注册表 | `reg export` 前置导出 | `reg import` | 中-高 |
| 服务操作 | `sc qc`+`sc query` 快照 | 按快照重建 | 中 |
| 计划任务 | `schtasks /export /xml` | `/create /xml` | 中-高 |
| git 仓库 | git 自身（reflog/branch tag），**push 类动作不入可回滚批次** | git 原生 | 高（仓库内） |
| 清空回收站 | **不可回滚** | — | 设计上排在最后一批，单独授权 |

### 2.2 操作日志（中断恢复的根基）
每个 run 一个 `operations.jsonl`，每行一条动作：
```json
{"runid":"20261025-143022-123","batch":2,"seq":17,"type":"move-to-quarantine",
 "from":"<盘符>:\\<项目根>\\_scratch\\old.log","to":"<盘符>:\\<隔离区>\\_quarantine\\20261025-143022-123\\<项目根>\\_scratch\\old.log",
 "size":12345,"sha256":"…","status":"done","ts":"…"}
```
- **状态机**：pending → done / failed。中断后重跑 = 读日志，done 跳过、pending 重做、failed 上报——**天然防重复删除/移动**（幂等：from 不在、to 在 = 已完成）。
- 执行前"前提检查"升级为**对象指纹核对**：manifest 哈希与现场不符（文件被改过/没了）→ 该批拒绝执行，报"计划与现场不符"（设计约束：计划或现场对象发生变化时须重新核对并重新批准）。

### 2.3 回退流程
```
rollback.ps1 -RunId <id> [-Batch N]   # 尚未实现：设计中的调用约定，当前按规程手工执行
  → 读 operations.jsonl → 过滤指定批次 → 逆序回放
  → 每步先校验隔离区对象哈希 → 移回原位 → 校验恢复结果
  → 输出回滚报告（成功 N / 失败 M / 因对象已变更而跳过 K）
```
> **该脚本尚未实现：以下为设计中的调用约定；当前需按本节规程手工执行。**

**回滚失败 ≠ 数据丢失**：对象还在隔离区，原路径手工恢复即可。每批执行后随机抽 2 条做"回滚演练"（设计约束：恢复能力必须经过实际演练验证）。

## 6. 交接脚本的可用性要求（2026-11-16 新增，实战教训）

本技能会产出"交给用户自己跑"的管理员脚本（如卸载服务、修 ACL）。这类脚本有个通病：
**用户看不到结果**。

### 6.1 提权窗口必须 `-NoExit`

```powershell
# ❌ 错的：脚本一结束，管理员窗口立刻关闭，最后的复核输出一闪而过
$argList = @("-NoProfile","-ExecutionPolicy","Bypass","-File","`"$PSCommandPath`"")

# ✅ 对的：窗口保留，用户可以看完再手动关
$argList = @("-NoProfile","-ExecutionPolicy","Bypass","-NoExit","-File","`"$PSCommandPath`"")
```

实测后果：某次服务卸载脚本实际**全部执行成功**，但用户只看到"删防火墙"那一步，
以为失败了，要求重新检查。窗口消失 = 用户无法判断成败 = 需要重新验证一遍。

### 6.2 复核段必须进日志，不能只 `Write-Host`

`Write-Host` 只上屏、不进文件。脚本末尾的"逐项复核"恰恰是最该留档的部分。

规矩：**同一份结果双写**——屏幕上用彩色便于当场判断，同时用日志函数追加到文件。
日志文件路径在末尾打印出来，用户和后续审查者都能回看。

### 6.3 脚本末尾留一个暂停

```powershell
Write-Host "按任意键关闭本窗口……" -ForegroundColor Gray
try { [void][Console]::ReadKey($true) } catch { Read-Host | Out-Null }
```

`-NoExit` 与暂停二者取其一即可，同时有也不冲突——暂停能保证"最后一行一定被看到"。

### 6.4 退出码要解读，不要只报数字

| 退出码 | 含义 | 判定 |
|---|---|---|
| 0 | 成功 | OK |
| 3010 | 成功但需重启 | OK（提示重启） |
| 1605 | 产品未安装 | 已经是目标状态 |
| 1603 | 致命错误 | FAIL，需查日志 |

只写"退出码: 3010"会让用户以为失败。

## 7. 删除验收：空间增量而非文件消失（2026-11-16 新增，两次实测踩坑）

### 7.1 问题

典型问题：大额清理报告"已删除"，用户去看资源管理器——**可用空间一点没变**，据此判定"清理失败"。

文件确实从原路径消失了。原因在删除路径不同：

| 路径 | 空间何时释放 |
|---|---|
| `Move-Item` 到同盘隔离区（两段式的标准动作） | 清空隔离区时 |
| Shell / 资源管理器 / 回收站 API | **清空回收站时**（回收站在同一盘，占的就是这块空间） |
| `Remove-Item` 直删 | 立即 |

所以"逻辑删除完成"与"磁盘可用空间增加"之间没有必然关系。用"文件是否还在原位"做验收，在回收站路径下**永远为真**——这是典型的假成功。

### 7.2 裁决

**验收口径只有一个：可用空间增量。**

```
逻辑释放 X GB / 实测释放 Y GB / 回收站 Z GB
```

- `X` 由 manifest 的 size 汇总得出（计划口径）
- `Y` 由批次前后的 `Win32_LogicalDisk.FreeSpace` 实测差值得出（唯一可信口径）
- `Z` 由 `<盘>:\$Recycle.Bin` 体量变化得出（解释 X 与 Y 的差额）

三者关系必须能对上：`X ≈ Y + Z`（容差 1%）。对不上就是有第三方占用/写入，如实报告，不许抹平。

### 7.3 实现约束

1. 批内删除一律 `Move-Item` 到隔离区，不走回收站——保住可回退性，也不产生回收站条目。
2. 若本批经由了回收站（用户手动删、软件自删），执行后立刻测回收站增量；清空回收站属不可回滚动作，按铁律 5 单独授权、排最后一批。
3. 每批记录 `free_before_gb` / `free_after_gb` / `recycle_delta_gb` 三个数进 operations.jsonl——**没这三个数就不算执行完成**。
4. 报告里的"已清理 N GB"必须写实测值；写不出来就写"逻辑释放 N GB，实测未释放（原因：<回收站/第三方占用>）"。

### 7.4 与两段式的关系

两段式执行（隔离区）天然规避了这个问题：删除动作只是同盘 rename，空间本就不该变化——**"没释放"在宽限期内是正确行为**，不是失败。真正释放发生在清空隔离区那一刻，验收也在那一刻做。

所以判读顺序是：
1. 批次执行后：看文件是否进隔离区（对象级验收），不看空间。
2. 清空隔离区后：看空间增量（空间级验收），三栏对齐。
